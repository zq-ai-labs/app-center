# DSH 应用中心与 AI 对话集成需求

Oct 24, 2026 · @sub.maureen

> 修订（2026-10-24）：对照 xbuddy（DSH）、bkms-workbench、xbuddy-bid-writer、bkms-plugin-center 源码和桌面 Profile 调整。主要变化：第 0、1 层改用 DSH 技能机制，对话工具减为 2 个；身份和角色复用 `@bkms/base`；回滚改为发修复版；补充现有入口清理。与现有代码的冲突和待验证项见文末两节。

> 修订（2026-10-25，应用中心只做框架）：应用中心只展示已安装并登记的应用，没有应用时显示空状态；不读取插件中心的目录和安装进度，也不提供重试。安装、升级、失败重试都只在插件中心内部完成。

## 背景与目标

在 DSH 客户端里做一个“应用中心”。合同、标书、业务邮件这类复杂功能都以 DSH 插件的形式提供，由插件中心（plugin-center）统一自动安装和升级；同时在 AI 对话中用一句话就能发起和查看它们。

要解决的问题：

- 复杂流程（合同评审、标书编写、邮件处理）没法在聊天里一步步做完，需要专门的页面和后台任务。
- 功能多了以后，AI 同时看到的工具和技能太多，调用会不准。
- 能力要经常上新，不能每次都发 300 多兆的客户端安装包。

目标：

1. 用户在应用中心浏览、打开应用；应用由插件中心自动装好，用户不需要手动安装。
2. 用户在对话中说一句话，AI 找到对应的应用，发起任务、查进度、看结论，并能一键打开应用页面。
3. AI 只按需加载应用的说明，不管装了多少应用，调用准确率都稳定。
4. 应用以插件包独立上线和升级（大多数 1MB 到几 MB；含原生依赖的应用例外），由插件中心自动下载；客户端大包只在底层大改时才发。

## 范围

| 本期做 | 本期不做 |
| --- | --- |
| 应用中心插件：登记、页面、对话工具（不负责安装升级） | 在对话里直接发送邮件或微信 |
| 对话集成：应用技能目录 + 两个通用工具 + 任务进度 | 在对话里跑完整的合同或标书流程 |
| 应用接入规范：清单格式、统一动作、风险级别、版本与打包 | 修改外部业务系统（ERP、OA 等） |
| 首批三个应用接入：业务邮件、合同、标书 | 第三方开发者上架应用 |
| 插件中心统一安装升级：离线种子首次安装、中心规则自动升级、失败重试 | 应用内部的具体业务功能（各应用单独出需求） |

| 清理现有入口：去掉预装的 dsh-email，企业用户关闭 dshmarket，明确各入口分工 | 微信往来的对话检索（本期 `mail.search` 只查邮件） |

## 核心概念

对话负责发起、查询和交接，真正的工作在应用页面和应用后台里完成。

| 概念 | 说明 |
| --- | --- |
| 应用 | 一个 DSH 插件，有自己的页面、后台任务和技能，如合同、标书、业务邮件 |
| 应用清单 | 每个应用向应用中心登记的一份说明：名称、一句话描述、动作、参数、版本。应用中心页面和 AI 都读它。权限和适用角色以服务端目录为准，不在清单里 |
| 动作 | 应用对外提供的业务操作。统一动作 start / list / get / status，每个应用另加不超过 3 个专有动作 |
| 任务 | 一次动作产生的工作（一次评审、一份标书），有任务 ID、状态、结论摘要和页面链接 |
| 风险级别 | 每个动作标一个：读 / 草稿 / 内部写。对外发送不提供动作，只在工作台人工审核后发出 |

**三层加载**：AI 不一次拿到所有应用的全部说明，而是逐层取用。第 0、1 层直接用 DSH 现有的技能机制（目录常驻、正文按需加载、对话中途追加新目录），不另做一套。

| 层 | AI 看到什么 | 什么时候进上下文 |
| --- | --- | --- |
| 0 目录 | 每个已安装应用一个技能条目（如 `app-contract`）：名称和一句话描述 | 一直在；插件中心装好或升级应用后，在对话中自动追加新目录 |
| 1 用法 | 一个应用的动作、参数、发起前要问什么、什么情况不用它 | AI 加载该应用技能时，或用户输入 `/app-<id>` 时 |
| 2 执行 | 动作结果：结论 + 链接；长任务返回任务 ID | 调用 `app_call` 时 |

应用内部也按需加载：每个应用的后台只带自己的工具和技能，按阶段读取（比如写技术方案章节时才读技术方案的写法）。主对话看不到这些细节。

**与企业知识调用的分工**：企业模式已有 `enterprise_invoke_function`（知识检索命中接口知识、后端鉴权后调用业务插件，目前用于智能问数）。本期分工为：一问一答的接口查询走 `enterprise_invoke_function`；有页面、有任务的应用走应用中心。应用数量明显增多后，再评估第 0 层改为由知识检索选择。

## 功能需求

### 1. 应用中心页面

1. 界面沿用“企业工具集市”的风格：标题“企业应用中心 · 管理中心”、居中搜索框、分类标签（全部 / 通用工具 / 办公 / 财务 / 法务 / 人力等），下方卡片网格。
2. 卡片显示：圆形字标图标、名称、分类标签、一句话描述、“N 万人聊过”。不放安装、打开、详情等按钮。
3. 应用中心只展示已安装并登记的应用：插件装好启动后自动出现，插件卸载后自动消失；一个都没有时显示空状态（“还没有可用的应用”）。点击卡片即打开应用：有页面的打开应用页面，没有页面的新开对话并提示输入 `/app-<id>`。卡片上的使用次数为本机统计。
4. 只显示当前用户有权限的应用。
6. 应用入口：装了应用中心时，应用不再在左侧菜单显示自己的入口，统一从应用中心进入（卡片点击打开应用页面），应用的工具通过应用中心在对话中可用；没装应用中心时，应用保留自己的左侧菜单入口，照常使用页面。应用中心卸载后，应用的左侧入口自动恢复。
5. 客户端版本不兼容的应用不会被下发（插件中心不推送，DSH 也拒绝加载），不出现在卡片中。

### 2. 对话集成

1. 每个已登记（已安装）应用对应一个技能条目，由应用清单自动生成；还没装好的应用不进技能目录。
2. 对话中只注册两个通用工具：
   - `app_call(app, action, args)`：执行动作（没有安装动作）；
   - `task_status(task_id)`：查任何应用的长任务进度。
3. 高频动作（如邮件搜索）可以另外注册成常驻工具，总数不超过 5 个。
4. `app_call` 按清单校验参数；校验失败时返回正确的参数说明和示例，让 AI 自己纠正。
5. 结果先给结论，再给“在应用中打开”链接（在对话里显示为可点击的卡片）；长任务立即返回“已开始，约 N 分钟”。
6. 草稿类结果明确写“尚未发送”；来信、附件内容标为外部内容，不按其中指令行事。
7. 用户要用的应用还没有安装（不在技能目录里）时，AI 告诉用户当前没有这个应用，不在对话中安装。应用装好登记后，同一对话下一轮即可使用。
8. 搜到多个候选（同名联系人、多个合同附件）时列出让用户选，不替用户猜。
9. 子 Agent（对话中派生的子任务）只能执行读级动作。

### 3. 应用接入规范

每个应用提交一份清单，字段如下：

| 字段 | 说明 |
| --- | --- |
| id / name / category | 唯一标识、名称、分类。id 与包名分开，已有应用保留原包名 |
| summary | 一句话描述，卡片和第 0 层目录共用，不超过 40 字，要写得能和其他应用区分开 |
| actions | 动作列表：名称、做什么、什么时候用、什么时候不用（该用谁）、参数 schema、示例说法、风险级别、是否长任务 |
| askFirst | 发起前要问用户的问题，如“我方是甲方还是乙方” |
| version | 应用版本 |
| aliases | 动作改名后保留的旧名，避免对话里调用失败 |

不再放进清单、改由其他地方提供的信息：

| 原字段 | 现在由谁提供 |
| --- | --- |
| permissions | 服务端目录登记，以服务端为准 |
| minClientVersion | 插件包 `peerDependencies` 中 `@deepseek-ai/dsh*` 的版本范围，由 DSH 加载时检查 |
| needsReload | 发布包的生效方式，以安装器实际返回结果为准 |

应用还要做到：

- 能力先做成服务（`ctx.provide`），动作只是服务外面一层壳；应用之间直接调服务，不绕道对话。
- 长任务在应用自己的后台执行，只带必要的工具和技能；用隔离 Agent 还是任务队列由应用决定。
- 任何对外发送都交给工作台“待我决策”，不自己发。
- `@deepseek-ai/dsh*` 的 peer 写版本范围，不写死精确版本，避免客户端一升级应用就被停用。
- 依赖全部打进发布包（`bundleDependencies`），内网安装不访问外部仓库；没有安装脚本。
- 左侧菜单入口只在没有应用中心时显示：客户端监听应用中心的存在服务（`bkmsAppCenter`），存在时撤下自己的入口、保留页面，消失时恢复入口。
- 在中心配置分发规则：必装（`installMode: required`）、自动升级（`autoUpgrade: true`）、适用角色、生效方式；发布包同时进入客户端的离线种子。
- 数据迁移只加不删，保证上一版应用也能读新数据。
- 数据放在 DSH 的 Profile 上下文（`ctx.profileContext`）下，按企业和用户隔离。

### 4. 安装与升级

所有插件（应用中心、业务应用和其他 BKMS 插件）的安装和升级都由插件中心（plugin-center）完成。应用中心、AI 对话和用户都不直接安装插件。

| 环节 | 方式 |
| --- | --- |
| 引导 | 插件中心本身由客户端安装包预装（XBuddy 预装清单只保留插件中心），随客户端大版本升级 |
| 首次安装 | 客户端安装包附带离线种子：各插件的 tgz 和一份初始分发规则。插件中心首次启动时从种子安装，不需要联网 |
| 新增与升级 | 客户端不升级时，插件中心按中心的分发规则在后台自动下载、校验、安装新版本和新增插件 |
| 生效 | 大多数应用热加载（`restart.mode = none`），装好后同一对话即可使用；需要刷新或重启的插件由插件中心统一提示 |

1. 不做按需下载：分发规则统一为必装、自动升级；按角色决定给谁下发哪些插件。
2. 服务端维护目录和分发规则：每个插件的最新版、兼容的客户端版本范围、大小、权限、适用角色、生效方式。
3. 下载的包校验大小与 SHA256，权限以服务端登记为准；是否另加签名见冲突 C5。
4. 后台升级时，应用在停用前保存进行中的长任务，新版启动后接着跑，或标为失败可重试。
5. 客户端版本不在插件声明的兼容范围内时，不推送新版（DSH 加载时也会拒绝）。
6. 支持分批上线和暂停分发；出问题时发布更高版本的修复版，不做降级安装。
7. 插件自己负责数据迁移，新版必须能读旧数据，迁移只加不删。
8. 离线种子同时用作内网部署的全量离线包；种子里的包预先放进插件中心缓存，同版本不再下载。
9. 应用中心不读取插件中心的目录和安装进度：应用装好并登记后才出现在应用中心；正在安装或安装失败的应用由插件中心自己的页面和提示处理。
10. 过渡：把现有 BKMS 插件从 XBuddy 预装清单移到离线种子之前，XBuddy 预装逻辑需改为“从清单移除的包不自动卸载”，由插件中心接管，避免启动时先被卸载（见分析文档）。

### 5. 权限与审计

1. 企业后台按角色设置给谁下发哪个应用（如法务有合同，投标部有标书）。用户身份和角色来自 `@bkms/base` 的企业登录。
2. 应用所需权限由管理员在中心上架时登记和确认，随分发规则下发。
3. 应用之间调用服务时，按服务端登记的权限把关：服务按能力拆分（只读和写分开提供）。
4. `app_call` 按动作的风险级别处理：读直接执行；草稿默认直接执行（发送前反正要在工作台审核）；内部写弹窗确认。AI 没有任何安装能力。
5. 从对话发起的草稿永远不进入工作台的自动发送，只能人工审核后发出。
6. 没有权限的应用不出现在应用中心和 AI 目录里。
7. 邮件和微信的可见范围沿用工作台的白名单和黑名单。
8. 每次对话调用都记入活动记录：哪次对话、哪个应用、哪个动作、产生了什么。

## 首批应用

首批接入三个应用。动作名称和参数是草案，待各应用出详细需求时定。

| 应用 | 动作 | 做什么 | 级别 |
| --- | --- | --- | --- |
| 业务邮件 mail | search | 按关键词、联系人、时间查邮件（常驻工具）；本期不含微信 | 读 |
| 业务邮件 mail | get | 读一封邮件，分离最新内容和历史引用 | 读 |
| 业务邮件 mail | list | 列出待决策、AI 已代办的事项 | 读 |
| 业务邮件 mail | draft\_reply | 为一封来信起草回复，放进“待我决策”，不发送、不进自动发送 | 草稿 |
| 业务邮件 mail | handoff | 把来信或附件交给合同、标书应用 | 草稿 |
| 合同 contract | start | 发起评审或起草（`mode`）；评审前确认我方立场 | 草稿 |
| 合同 contract | list / get / status | 我的合同项目、风险摘要、进度 | 读 |
| 合同 contract | templates | 列出可用模板 | 读 |
| 标书 bid | start | 传入招标文件，建立标书项目并解析 | 草稿 |
| 标书 bid | list / get / status | 项目列表；资格要求、评分项、废标项、章节进度 | 读 |
| 标书 bid | check | 检查标书对招标要求的响应是否完整 | 读 |

各应用接入还需要的改动（不只是加一段登记）：

| 应用 | 现状 | 需要补 |
| --- | --- | --- |
| 业务邮件（bkms-workbench） | 已提供只读服务 `workbenchMail` v1：accounts / search / read（直接搜邮件服务器） | 待决策事项列表；对任意来信建任务并生成草稿（不自动发送）；按引用交出附件 |
| 标书（xbuddy-bid-writer） | 已提供服务 `ctx.bid`，但建项目只接受 HTTP 上传请求 | 按附件引用建项目并开始解析；把现有快照包装成 list / get / check；peer 改为版本范围 |
| 合同 | 尚无代码 | 按本规范新建 |

典型场景：

1. “找一下和启明演示关于 TH-100 的往来” → `mail.search`。
2. “我今天有哪些要决策的” → `mail.list`。
3. “给这封询价起个回复” → `mail.draft_reply`，结果在待我决策。
4. “把这封邮件的合同附件审一下，我们是乙方” → `mail.handoff` → 合同评审任务。
5. “按这份招标文件开始做标书” → `bid.start`，返回项目链接。
6. “标书还差哪些没响应” → `bid.check`。

以下接口在 DSH 源码或现有插件中已经确认可用，大部分需求不需要改 DSH 核心。

| 需求 | DSH 接口 | 确认情况 |
| --- | --- | --- |
| 应用登记，应用之间调用 | `ctx.provide('appCenter', …)` / `ctx.inject(['appCenter'], …)` | 工作台、标书已在用 |
| 第 0、1 层（技能目录与按需加载） | `ctx.skills.register(...)` + 宿主的 `skill` 工具 | 机制已确认；企业模式下能否看到插件注册的技能待验证 |
| 两个通用工具 + 常驻工具 | `ctx.tools.register({ name, description, parameters, output, execute })` | 已确认；新注册的工具下一步即生效 |
| 按风险级别放行 / 弹窗 | `ctx.on('tools/pre-execute', …)` 返回 `{ kind: 'ask' }`，用宿主自带审批界面 | 已确认 |
| 结果卡片和链接 | 工具 `output.presentationMeta` + 客户端注册 `tool.call.toolview` | 已确认，需应用中心提供客户端渲染组件 |
| 对话 ID 和发起者 | `exec.agent.session.header`（含 id、是否子 Agent） | 已确认 |
| 当前用户和角色 | `ctx.bkmsApi.auth.user`（tenantCode、userId）、客户端 `bkmsAuthUi.getRoleIds()` | 已确认 |
| 应用后台长任务 | `agents.create(...)` 限定工具，或应用自己的任务队列 | 工作台、标书分别在用 |
| 新开对话并预填 | `uiWorkspace.startSession()` + 输入框草稿替换 | 接口存在，需在客户端串联 |
| 应用中心页面和接口 | `ctx.connection.fetch.register({ path, methods })` + 客户端页面 | 已确认 |
| 安装、升级、重试 | 只由 bkms-plugin-center 执行（DSH 插件热插拔）；应用中心不连接插件中心 | 已确认；离线种子已实现 |
| 客户端版本兼容 | DSH 0.2.0 检查 `peerDependencies` 中的 `@deepseek-ai/dsh*`；0.2.1 起声明了 `engines.dsh` 时只看它 | 已确认 |

## 与现有代码的冲突

## 验收标准与分阶段计划

### 验收标准

以下数值为建议值，评审时确认。

- [ ] 建立测试集：不少于 50 句真实说法，标注应选的应用和动作，也包括“不该调用”“应先反问”和“应走企业知识调用”的情况。
- [ ] 应用和动作的选择准确率不低于 90%，每次新增应用或动作前都要跑一遍。
- [ ] 应用中心在主对话常驻的工具不超过 7 个（2 个通用工具 + 不超过 5 个常驻动作）。
- [ ] 第 0 层目录每个应用一条，描述不超过 40 字。
- [ ] 插件中心安装或升级热加载类应用后，不重启就能在当前对话中使用。
- [ ] 断网环境首次启动，离线种子中的插件全部装好；对话和应用中心都没有安装入口。
- [ ] 对话中没有任何对外发送的动作（含去掉 dsh-email）；草稿结果都写明“尚未发送”，且不进自动发送。
- [ ] 插件升级时进行中的任务可续跑或明确标为可重试；新版能读旧数据，上一版能读新版数据。
- [ ] 客户端升级到兼容范围内的新版本后，已装应用无需重新发布即可继续使用。

### 分阶段计划

4 个阶段，3 个闸口。日期待定。

```
阶段零 原型验证 ──闸口 1──► 阶段一 对话集成 ──闸口 2──► 阶段二 分发与权限 ──闸口 3──► 阶段三 扩展
```

| 阶段 | 用户能得到什么 | 范围 |
| --- | --- | --- |
| 阶段零 原型验证（约 1 周） | 无（内部验证） | 在真实桌面版上完成 V1–V4，确定第 0、1 层的实现方式 |
| 阶段一 对话集成 | 业务邮件、标书可在对话中查找、起草、发起和查进度 | 应用中心和业务邮件；去掉预装 dsh-email；标书改 peer / `engines.dsh` 版本范围和依赖打包 |
| 阶段二 统一分发与权限 | 应用随客户端自动装好、平时自动升级；按角色下发 | 插件中心离线种子与服务（目录、状态、重试）；XBuddy 预装清单只留插件中心、预装不自动卸载；中心服务按角色过滤、分批上线和暂停；关闭 dshmarket |
| 阶段三 扩展 | 合同评审和起草可在对话中发起 | 合同应用接入；评估第 0 层改由知识检索选择 |

| 闸口 | 通过条件 |
| --- | --- |
| 闸口 1（阶段零 → 一） | V1–V4 有结论，第 0、1 层实现方式确定 |
| 闸口 2（阶段一 → 二） | 测试集准确率不低于 90%；对话中没有发送动作；对话草稿不进自动发送 |
| 闸口 3（阶段二 → 三） | 没权限的应用不出现；断网首次启动从种子装好；后台升级不降级；暂停分发和修复版流程演练通过 |

阶段一只动应用中心和业务邮件，可以和合同、标书应用的开发同时进行。
