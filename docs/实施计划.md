## 实现顺序

1. 应用中心核心（纯逻辑，可单测）：清单校验、参数校验、注册表、技能文本、风险决策、任务索引、审计。
2. 应用中心插件入口：把核心接到 DSH 接口（`ctx.provide`、`ctx.tools.register`、`tools/pre-execute`、`ctx.skills.register`、`ctx.connection.fetch.register`），所有宿主服务都按可选处理。
3. 应用中心页面和结果卡片（客户端）。
4. 演示环境，跑通需求文档的典型场景。
5. 工作台、标书、插件中心的接入改动，各自在功能分支上提交。
6. 把应用中心链接进本机 XBuddy 桌面 Profile（先备份），重启后可见。

## 验收

- 单元测试全部通过。
- 演示环境中：应用中心页面能浏览、搜索、安装（模拟）、打开应用；对话调试面板能看到技能目录、技能正文、`app_call` 结果和风险决策；发送类动作登记被拒绝；子 Agent 调用写级动作被拒绝。
- 工作台、标书的类型检查和原有测试通过。

在真实 DSH 中发现并已修复的问题：

- 在 Cordis 4 中，读取没有通过 `inject` 声明的服务属性（如 `ctx.profileContext`、`ctx.logger`）会直接抛错，插件启动失败。模拟宿主没有暴露这个问题，现已改为只通过 `ctx.get` / `ctx.inject` 读服务，模拟宿主也改成同样严格。两个接入适配器的日志读取同样做了保护。
- `ctx.provide('appCenter', value)` 在真实 Cordis 中可用（技术方案“工作台 `workbenchMail` 未验证”一项的同类问题），`ctx.get` 只返回已启动插件提供的服务。

待验证项进展：

- V1：真实技能注册表接受应用技能并按需返回正文；在企业模式技能目录中是否可见，仍需在桌面版界面确认。
- V2：工具结果的 `meta`（卡片数据）在真实工具注册表中正确产出；客户端卡片渲染需在桌面版确认。
- V9：全局注册的工具在真实注册表中可见，子 Agent 拦截在真实 `tools/pre-execute` 流水线中生效。

## 应用中心只做框架（第三轮，2026-10-25）

应用中心只展示已安装并登记的应用，没有应用时显示空状态；不再读取插件中心的目录和安装进度，也没有重试接口。

| 模块 | 改动 | 验证 |
| --- | --- | --- |
| 应用中心 | 去掉中心目录读取、同步状态推算、重试接口和对插件中心的依赖；页面只列已登记应用，空状态隐藏分类、禁用搜索；卡片使用次数为本机统计；示例模式改为合同几秒后登记 | 16 项测试通过：空应用中心、应用登记后出现与注销后消失（含技能、对话调用、历史任务仍可查）、真实插件中心同步引擎从种子安装后应用登记并出现；演示页面验证了应用出现、全部移除后的空状态和重新出现 |
| 插件中心 | 去掉给应用中心用的只读服务 `bkmsPluginCenter` 和目录回退；离线种子保留 | 种子测试 4 项通过 |

## 已知限制

- 演示环境里的“AI”是脚本化调用，用来展示模型实际收到的内容；真实模型效果要在桌面版上验证。
- 本机 Profile 未安装工作台和插件中心，桌面版里能看到的是应用中心页面和标书助手；工作台需要配置邮箱后再接入。
